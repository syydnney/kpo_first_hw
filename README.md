# ВышКат — система учёта парка кикшеринга

## 1. Описание проекта

«ВышКат» — консольное приложение на C# для учёта транспортных средств и инвентаря сервиса кикшеринга.

Программа позволяет:

- Добавлять транспорт в парк после прохождения технического осмотра.
- Отклонять транспорт, не прошедший техосмотр.
- Учитывать электросамокаты, велосипеды и электровелосипеды.
- Добавлять на баланс шлемы и зарядные станции.
- Контролировать уникальность инвентарных номеров.
- Рассчитывать суммарное суточное энергопотребление.
- Получать список транспорта, подходящего для новичков.
- Просматривать отчёты по парку и полный список инвентаря.

Транспорт подходит новичкам, если показатель простоты управления находится в диапазоне от 6 до 10.

Данные хранятся в оперативной памяти и не сохраняются после завершения работы приложения.

## 4. Сборка и запуск

Для работы требуется установленный .NET 10 SDK.

Клонирование репозитория:

```bash
git clone https://github.com/syydnney/kpo_first_hw.git
cd kpo_first_hw
```

Восстановление зависимостей:

```bash
dotnet restore
```

Сборка проекта:

```bash
dotnet build
```

Запуск консольного приложения:

```bash
dotnet run --project src/VyshKat.Console
```

После запуска пользователю доступно меню:

```text
=== ВышКат ===
1. Добавить транспорт
2. Добавить инвентарь
3. Отчёт по парку
4. Транспорт для новичков
5. Весь инвентарь
0. Выход
```

## 5. Архитектура приложения

### 5.1. Доменная модель

Абстрактный класс `InventoryItem` содержит общие свойства инвентаризируемых объектов:

- `InventoryNumber` — инвентарный номер.
- `Name` — наименование.

От него наследуются транспортные средства и инвентарные вещи.

Абстрактный класс `Transport` расширяет `InventoryItem` и добавляет:

- `EaseOfUse` — простота управления от 1 до 10.
- `IsSuitableForBeginners` — пригодность для новичков.
- `IsTechnicallySound` — признак технической исправности.

Конкретные виды транспорта реализованы отдельными классами: `Scooter`, `Bicycle` и `ElectricBicycle`.

Инвентарь представлен классами `Helmet` и `ChargingStation`.

### 5.2. Интерфейсы

В проекте используются три основных интерфейса.

`IInventoryItem` задаёт общий контракт для инвентаризируемых объектов.

`IEnergyConsumer` содержит свойство `DailyEnergyConsumption`, позволяющее учитывать расход электроэнергии независимо от типа устройства.

`IServiceCenter` определяет метод `Inspect`, который возвращает результат техосмотра транспортного средства.

### 5.3. Бизнес-логика

Основной сервис `FleetService` отвечает за:

- Приёмку транспорта.
- Добавление инвентаря.
- Контроль уникальности инвентарных номеров.
- Подсчёт транспорта и всех инвентарных объектов.
- Расчёт энергопотребления.
- Получение транспорта для новичков.

При добавлении транспорта `FleetService` обращается к `IServiceCenter`.

Если техосмотр не пройден, транспорт не добавляется в парк.

В реализации `ServiceCenter` проверяет свойство `IsTechnicallySound`. Это упрощённая модель технического осмотра.

## 6. Применение принципов SOLID

### S — Single Responsibility Principle

Классы имеют разделённые обязанности.

`FleetService` управляет парком, `ServiceCenter` выполняет техосмотр, а `ConsoleApp` отвечает за взаимодействие с пользователем.

Это позволяет изменять консольный интерфейс без изменения правил управления парком.

### O — Open/Closed Principle

Система допускает добавление новых видов транспорта через наследование от `Transport`.

Методы `FleetService` работают с базовым типом `Transport`, поэтому при добавлении нового транспортного средства их изменять не требуется.

Однако для добавления нового типа в пользовательское меню необходимо дополнить `ConsoleApp`.

### L — Liskov Substitution Principle

Объекты `Scooter`, `Bicycle` и `ElectricBicycle` могут использоваться вместо базового типа `Transport`.

Все классы транспорта предоставляют общий набор свойств и подчиняются одинаковым правилам приёмки.

### I — Interface Segregation Principle

Функциональность разделена на небольшие интерфейсы.

Например, обычный велосипед и шлем не реализуют `IEnergyConsumer`, поскольку не потребляют электричество.

В то же время электросамокат и зарядная станция реализуют этот интерфейс, хотя относятся к разным категориям объектов.

### D — Dependency Inversion Principle

`FleetService` зависит от интерфейса `IServiceCenter`, а не от конкретной реализации `ServiceCenter`.

Зависимость передаётся через конструктор.

В `Program.cs` используется DI-контейнер, который регистрирует необходимые сервисы и создаёт их экземпляры.

Это также позволяет заменять реализацию техосмотра при тестировании.

## 7. Dependency Injection

Для внедрения зависимостей используется `Microsoft.Extensions.DependencyInjection`.

В `Program.cs` регистрируются:

```csharp
services.AddSingleton<IServiceCenter, ServiceCenter>();
services.AddSingleton<FleetService>();
services.AddSingleton<ConsoleApp>();
```

`FleetService` получает объект, реализующий `IServiceCenter`, через конструктор.

Для тестирования используется `FakeServiceCenter`, позволяющий заранее определить результат техосмотра.

Это обеспечивает возможность тестировать работу `FleetService` независимо от реального `ServiceCenter`.

## 8. Юнит-тестирование

Тестирование реализовано с помощью xUnit.

Проверяются следующие сценарии:

- Успешное добавление транспорта.
- Отклонение транспорта после неуспешного техосмотра.
- Запрет дублирования инвентарных номеров.
- Добавление инвентаря.
- Запрет обхода техосмотра.
- Корректность расчёта энергопотребления.
- Выбор транспорта для новичков.
- Проверка допустимых значений конструктора.
- Обработка некорректных значений энергопотребления.

Для подмены техосмотра используется `FakeServiceCenter`.

## 9. Ответы на обязательные вопросы

### 9.1. Какой принцип SOLID применён наиболее явно и где?

Наиболее явно реализован принцип Dependency Inversion Principle (DIP).

Класс `FleetService` зависит от интерфейса `IServiceCenter`, благодаря чему конкретная реализация техосмотра может изменяться без изменения логики управления парком.

### 9.2. Какой принцип сознательно ограничен и почему?

Частично ограничен принцип Open/Closed Principle (OCP) в классе `ConsoleApp`.

При добавлении нового вида транспорта необходимо дополнить меню и логику создания объекта.

Это решение принято сознательно, поскольку приложение небольшое. Использование дополнительного слоя фабрик и сложных механизмов регистрации видов транспорта привело бы к неоправданному усложнению архитектуры.

### 9.3. Что произойдёт при добавлении нового транспорта, сотрудника или склада?

При добавлении нового транспорта необходимо создать класс, наследующий `Transport`.

Основной сервис `FleetService` останется без изменений, но потребуется дополнить консольный интерфейс.

При добавлении сотрудников необходимо создать отдельную модель, не наследующую `InventoryItem`, поскольку сотрудники не являются инвентаризируемыми объектами.

Для полноценного склада запчастей потребуется отдельная модель складских позиций и сервис учёта остатков.

### 9.4. Какие тесты фиксируют решение техосмотра и правило для новичков?

Методы `AddTransport_AcceptsTransport_WhenInspectionPasses` и `AddTransport_RejectsTransport_WhenInspectionFails` проверяют результат технического осмотра.

Метод `GetBeginnerTransport_ReturnsOnlySuitableTransport` проверяет, что в список для новичков попадают только подходящие транспортные средства.

Для подмены зависимости используется `FakeServiceCenter`, который передаётся в конструктор `FleetService`.

### 9.5. Как использовался ИИ?

При выполнении работы ИИ-агент применялся для реализации юнит-тестов и формирования документации.

Созданные юнит-тесты интегрировались в проект с последующей проверкой сборки, запуском.
